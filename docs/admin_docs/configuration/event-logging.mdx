# Logging

## Event Logging

Superset by default logs special action events in its internal database (DBEventLogger). These logs can be accessed
on the UI by navigating to **Security > Action Log**. You can freely customize these logs by
implementing your own event log class.
**When custom log class is enabled DBEventLogger is disabled and logs
stop being populated in UI logs view.**
To achieve both, custom log class should extend built-in DBEventLogger log class.

Here's an example of a simple JSON-to-stdout class:

```python
    def log(self, user_id, action, *args, **kwargs):
        records = kwargs.get('records', list())
        dashboard_id = kwargs.get('dashboard_id')
        slice_id = kwargs.get('slice_id')
        duration_ms = kwargs.get('duration_ms')
        referrer = kwargs.get('referrer')

        for record in records:
            log = dict(
                action=action,
                json=record,
                dashboard_id=dashboard_id,
                slice_id=slice_id,
                duration_ms=duration_ms,
                referrer=referrer,
                user_id=user_id
            )
            print(json.dumps(log))
```

End by updating your config to pass in an instance of the logger you want to use:

```
EVENT_LOGGER = JSONStdOutEventLogger()
```

## StatsD Logging

Superset can be configured to log events to [StatsD](https://github.com/statsd/statsd)
if desired. Most endpoints hit are logged as
well as key events like query start and end in SQL Lab.

Superset can also collect gunicorn [metrics](https://gunicorn.org/instrumentation/).
To enable these, the following environment variables should be set:

```bash
SERVER_STATSD_HOST=localhost
SERVER_STATSD_PORT=8125
SERVER_STATSD_PREFIX=superset
```

To setup StatsD logging for Superset, it’s a matter of configuring the logger in your `superset_config.py`.

```python
import os
from superset.stats_logger import StatsdStatsLogger

try:
    STATSD_PORT = int(os.environ.get("SERVER_STATSD_PORT", "8125"))
except ValueError:
    STATSD_PORT = 8125

STATS_LOGGER = StatsdStatsLogger(
    host=os.environ.get("SERVER_STATSD_HOST", "localhost"),
    port=STATSD_PORT,
    prefix=os.environ.get("SERVER_STATSD_PREFIX", "superset"),
)
```

[statsd](https://pypi.org/project/statsd/) in version ~3.3.0 must be installed.

Note that it’s also possible to implement your own logger by deriving
`superset.stats_logger.BaseStatsLogger`.

### Chart data latency metrics

The chart data API (`/api/v1/chart/data` and `/api/v1/chart/<pk>/data/`) emits
timers (in milliseconds) and counters that break a request down by phase, so
dashboard latency can be attributed to Superset processing, the results cache,
or the database. Keys are static; the only dimension encoded in a key is the
database engine name, a bounded set.

The endpoint as a whole is timed by the generic REST API timers
`ChartDataRestApi.data.time` and `ChartDataRestApi.get_data.time`. Phases nest,
so durations from different levels overlap and should not be summed across
levels.

| Metric | Type | Measures |
| --- | --- | --- |
| `chart_data.auth` | timer | Authentication and permission checks (`@protect`) before the handler runs |
| `chart_data.chart_lookup` | timer | Loading the saved chart (`GET /chart/<pk>/data/` only) |
| `chart_data.dashboard_filters` | timer | Resolving dashboard filter context (`filters_dashboard_id` only) |
| `chart_data.query_context.build` | timer | Parsing the request into a query context, including loading the datasource |
| `chart_data.query_context.validate` | timer | Object-level access checks on the query context |
| `chart_data.async.submit` | timer | Scheduling async query tasks (when the request returns 202) |
| `chart_data.command.execute` | timer | Running every query of the request (synchronous path) |
| `chart_data.totals` | timer | Contribution totals query, when a chart needs one |
| `chart_data.query.total` | timer | One query from validation through payload assembly |
| `chart_data.query.planning` | timer | Query validation, cache key and force resolution |
| `chart_data.cache.key` | timer | Computing the results cache key (includes template rendering for extra cache keys) |
| `chart_data.cache.get` | timer | Reading the results cache backend, including deserialization |
| `chart_data.cache.hit` / `.miss` / `.bypass` | counter | Results cache outcome; `bypass` is a forced refresh or a disabled cache |
| `chart_data.query.data_acquisition` | timer | Fetching data from the datasource on a cache miss or bypass |
| `chart_data.query.annotations` | timer | Loading annotation layer data on a cache miss or bypass |
| `chart_data.cache.set` | timer | Serializing and writing a fresh result to the results cache |
| `chart_data.query.payload_assembly` | timer | Building the per-query response payload |
| `chart_data.response.serialize` | timer | JSON-encoding the response body |
| `datasource.query.sql_generation` | timer | Building and rendering the SQL for a query |
| `datasource.query.normalize` | timer | Normalizing temporal and metric columns of the result |
| `datasource.query.time_offsets` | timer | Time comparison queries and joins |
| `datasource.query.post_processing` | timer | Pandas post-processing operations |
| `database.connect.<engine>` | timer | Opening a database connection |
| `database.execute.<engine>` | timer | Driver `execute` call for one statement; with drivers whose `execute` blocks until the query completes, this includes database queueing and execution |
| `database.fetch.<engine>` | timer | Fetching result rows from the driver |
| `database.dataframe.<engine>` | timer | Building the pandas DataFrame from fetched rows |

The `datasource.*` and `database.*` timers are emitted by shared query
execution code, so they also cover other features that query datasources
through the same path. Async chart queries emit the `chart_data.query.*`,
`chart_data.cache.*`, `datasource.*` and `database.*` metrics from the worker.

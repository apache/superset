This page describes how to install Superset using the `apache_superset` package [published on PyPI](https://pypi.org/project/apache_superset/).

## Python Compatibility

The minimum Python version is 3.11. The Python version classifiers in
[pyproject.toml](https://github.com/apache/superset/blob/master/pyproject.toml)
list the officially supported versions; the open-ended `requires-python` lower
bound does not certify every newer interpreter.

The source checkout includes experimental Python 3.15 compatibility. Its package
requirements select NumPy `>=2.5.4,<2.6` and pandas `>=3.1.0,<3.2` on Python 3.15
and newer. Python 3.11 through 3.14 retain NumPy `>=1.23.5,<2.5` and pandas
`>=2.3.3,<2.4`; the minimum Python version has not changed. These source changes
do not imply that an already published PyPI release supports Python 3.15.

The focused
[compatibility workflow](https://github.com/apache/superset/blob/master/.github/workflows/python-metadata-compatibility.yml)
tests Python 3.11 through 3.15. It installs the application without dependency
overrides, checks dependency consistency, migrates a fresh SQLite metadata
database, checks `/health`, and runs engine metadata, pandas post-processing
(including Prophet), result-set, and core SDK tests. The same 278 tests and fresh
SQLite migrations passed locally on Windows for all five interpreter versions,
including CPython 3.15.0 final.

A local Podman container running Debian 13 with CPython 3.15.2 also passed
336 focused tests, including the additional DataFrame serialization tests.
Installation without dependency overrides, dependency consistency, a fresh
SQLite migration to head, and the application health check succeeded. The
extended-precision `longdouble` regression passes on Linux.

The same isolated Linux environment also migrated a PostgreSQL 17 metadata
database to head and initialized the application and test users. Selected Redis 7
cache and synchronous/asynchronous query tests passed with a real Celery prefork
worker. All 35 tests in the selected CSRF/login, SQL Lab execution, cache-manager,
chart-cache, and Celery groups passed, including CTAS and CVAS operations. The
test database requires the configured `sqllab_test_db` schema. The CSRF tests
explicitly distinguish public endpoint access from access requiring login, and
the SQL Lab tests use synchronous mocks for the results backend.

A complete local run of `tests/common` and `tests/unit_tests` on CPython 3.15.2
finished with 32,821 passed, 57 skipped, 5 expected failures, and no unexpected
failures. Translation tests require complete frontend sources with LF line
endings and a Git checkout; cron description expectations use `en_US.UTF-8`.
This final run includes the raw-cursor join truncation fix. All 22 dialect tests
also passed on both Python 3.11 and 3.15, covering SQLAlchemy, direct iteration,
and all three fetch methods.
The earlier follow-up regression group also passed 1,683 tests on Python 3.11,
and the nine selected CSRF/login and SQL Lab tests passed on that version.

The production frontend build succeeded with Node 24.16.0 and webpack 5.112.0
(four warnings). Chromium acceptance passed all 24 selected Playwright tests
without retries: login success and rejection, chart management and ZIP export,
dashboard management and import/export, three chart types rendered from real
queries (including an ECharts canvas-pixel assertion), and SQL Lab query,
tab, saved-query, dataset, and Explore workflows. The browser server used
Gunicorn, PostgreSQL 17, Redis 7, `TESTING=False`, and enabled CSRF protection.
The browser dataset used 1,200 locally generated `birth_names` rows; chart
management tests additionally used the bundled Slack dataset metadata, without
claiming Slack data-query coverage.

Broader integration testing also covers the schema-free database SELECT route
without introducing a new permission, validates generated and published OpenAPI
path parameters, and rejects a missing embedded-dashboard referrer when an
allowed-origin list is configured. The referrer regression and the surrounding
database API/schema tests passed on Python 3.11 as well (41 selected tests).
The legacy Flask-Testing live server uses an explicit local `fork` context on
platforms that support it; this does not change application or Celery process
defaults. Thumbnail image generation remains outside this acceptance scope.

A complete local run of `tests/integration_tests` on CPython 3.15.2 finished
with 3,131 passed, 178 skipped, and no failures in 673 seconds. It used a fresh
PostgreSQL 17 metadata database, Redis 7, and a real Celery prefork worker with
a Redis SQL Lab results backend. Skipped tests remain unvalidated; a passing
collection does not establish support for every optional database or feature.

Earlier runs on the 8 GB Podman VM were invalidated by kernel-confirmed
out-of-memory worker termination. The successful final unit run used 16 GB;
browser and full unit acceptance ran separately. The local Hyper-V storage
also showed intermittent I/O errors, so this host is not a production reference.

Integration reruns require a fresh, migrated test metadata database: interrupted
or focused runs can leave fixtures that invalidate exact object-count assertions.
Keep browser acceptance in a separate database and Redis namespace. A real SQL
Lab worker also needs `RESULTS_BACKEND`, in addition to the Celery broker and
result-backend settings; verify these in both the test and worker processes.

All applicable pre-commit hooks passed for the changed files in Linux, including
MyPy, Ruff, formatting, YAML, and the advisory workflow audit. Pylint passed when
run explicitly against the changed application modules with `--jobs=1`; its
parallel serialization path uses a code-object attribute removed in Python 3.15.

For Python 3.15 testing, install from the source checkout's package metadata,
rather than applying the generated Python 3.11 requirement pins:

```bash
python -m pip install -e ./superset-core -e .
```

Run this command from the repository root in an isolated Python 3.15 environment.
Some dependencies require source builds, so a working C/C++ toolchain may be
needed. Windows validation used the x64 Visual Studio 2022 Build Tools. The
generated requirement files remain tied to the existing Python 3.11 deployment
baseline and are not Python 3.15 lock files.

This validation is not a full production certification. The remote Linux CI
jobs, skipped integration cases, the full database-driver matrix,
live report delivery and screenshot workflows, and browser workflows
beyond the selected 24 acceptance cases still require validation. Production
acceptance must also cover the target deployment's authentication, secrets,
network/TLS configuration, workload, backup/restore, and availability requirements.
An additional Windows
DataFrame test assumes extended `longdouble` precision unavailable on that
platform; Windows also exposes existing Unix-signal type-checking limitations.
Use an officially supported Python version for production deployments until
these broader compatibility checks have been completed.

## OS Dependencies

Superset stores database connection information in its metadata database. For that purpose, we use
the cryptography Python library to encrypt connection passwords. Unfortunately, this library has OS
level dependencies.

**Debian and Ubuntu**

The following command will ensure that the required dependencies are installed (tested on Ubuntu 20.04, 22.04, and 24.04):

```bash
sudo apt-get install build-essential libssl-dev libffi-dev python3-dev python3-pip python3-venv libsasl2-dev libldap2-dev libpq-dev default-libmysqlclient-dev pkg-config
```

Refer to the
[pyproject.toml](https://github.com/apache/superset/blob/master/pyproject.toml) file for the list of
Python versions officially supported by Superset, and install a matching `python3` interpreter for
your distribution. The `libpq-dev` package is only needed if you intend to connect to (or use) a
PostgreSQL database; you can omit it otherwise.

**Fedora and RHEL-derivative Linux distributions**

Install the following packages using the `yum` package manager:

```bash
sudo yum install gcc gcc-c++ libffi-devel python3-devel python3-pip python3-wheel openssl-devel cyrus-sasl-devel openldap-devel
```

In more recent versions of CentOS and Fedora, you may need to install a slightly different set of packages using `dnf`:

```bash
sudo dnf install gcc gcc-c++ libffi-devel python3-devel python3-pip python3-wheel openssl-devel cyrus-sasl-devel openldap-devel
```

Also, on CentOS, you may need to upgrade pip for the install to work:

```bash
pip3 install --upgrade pip
```

**Mac OS X**

If you're not on the latest version of OS X, we recommend upgrading because we've found that many
issues people have run into are linked to older versions of Mac OS X. After updating, install the
latest version of XCode command line tools:

```bash
xcode-select --install
```

We don't recommend using the system installed Python. Instead, first install the
[homebrew](https://brew.sh/) manager and then run the following commands:

```bash
brew install readline pkg-config libffi openssl mysql postgresql@14
```

You should install a recent version of Python. Refer to the
[pyproject.toml](https://github.com/apache/superset/blob/master/pyproject.toml) file for a list of Python
versions officially supported by Superset. We'd recommend using a Python version manager
like [pyenv](https://github.com/pyenv/pyenv)
(and also [pyenv-virtualenv](https://github.com/pyenv/pyenv-virtualenv)).

Let's also make sure we have the latest version of `pip` and `setuptools`:

```bash
pip install --upgrade setuptools pip
```

Lastly, you may need to set LDFLAGS and CFLAGS for certain Python packages to properly build. You can export these variables with:

```bash
export LDFLAGS="-L$(brew --prefix openssl)/lib"
export CFLAGS="-I$(brew --prefix openssl)/include"
```

These will now be available when pip installing requirements.

## Python Virtual Environment

We highly recommend installing Superset inside of a virtual environment.

You can create and activate a virtual environment using the following commands. Ensure you are using a compatible version of python. You might have to explicitly use for example `python3.11` instead of `python3`.

```bash
# virtualenv is shipped in Python 3.6+ as venv instead of pyvenv.
# See https://docs.python.org/3.6/library/venv.html
python3 -m venv venv
. venv/bin/activate
```

Or with pyenv-virtualenv:

```bash
# Here we name the virtual env 'superset'
pyenv virtualenv superset
pyenv activate superset
```

Once you activated your virtual environment, all of the Python packages you install or uninstall
will be confined to this environment. You can exit the environment by running `deactivate` on the
command line.

### Installing and Initializing Superset

First, start by installing `apache_superset`:

```bash
pip install apache_superset
```

Then, define mandatory configurations, SECRET_KEY and FLASK_APP:

```bash
export SUPERSET_SECRET_KEY=YOUR-SECRET-KEY # For production use, make sure this is a strong key, for example generated using `openssl rand -base64 42`. See https://superset.apache.org/admin-docs/configuration/configuring-superset#specifying-a-secret_key
export FLASK_APP=superset
```

Then, you need to initialize the database:

```bash
superset db upgrade
```

Finish installing by running through the following commands:

```bash
# Create an admin user in your metadata database (use `admin` as username to be able to load the examples)
superset fab create-admin

# Load some data to play with
superset load_examples

# Create default roles and permissions
superset init

# To start a development web server on port 8088, use -p to bind to another port
superset run -p 8088 --with-threads --reload

# For debugging with interactive console (⚠️ localhost only)
# superset run -p 8088 --with-threads --reload --debugger
```

:::warning Security Note
The `--debugger` flag enables Werkzeug's interactive console at `/console`. Only use this for local development and never bind to `0.0.0.0` or expose the server to networks when debugging is enabled.
:::

If everything worked, you should be able to navigate to `hostname:port` in your browser (e.g.
locally by default at `localhost:8088`) and login using the username and password you created.

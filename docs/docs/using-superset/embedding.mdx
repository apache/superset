# Embedding Superset

Superset dashboards can be embedded directly in host applications using the `@superset-ui/embedded-sdk` package.

:::info Prerequisites

- The `EMBEDDED_SUPERSET` feature flag must be enabled.
- The embedding domain and allowed origins must be configured by an admin.
  :::

## Quick Start

Install the SDK:

```bash
npm install @superset-ui/embedded-sdk
```

Embed a dashboard:

```javascript
import { embedDashboard } from '@superset-ui/embedded-sdk';

embedDashboard({
  id: 'dashboard-uuid-here', // from Dashboard → Embed
  supersetDomain: 'https://superset.example.com',
  mountPoint: document.getElementById('superset-container'),
  fetchGuestToken: () => fetchTokenFromYourBackend(),
  dashboardUiConfig: {
    hideTitle: true,
    filters: { expanded: false },
  },
});
```

`fetchGuestToken` must return a **guest token** obtained from your server by calling Superset's `/api/v1/security/guest_token/` endpoint with a service account. Do not call this endpoint from client-side code.

## Guest data access

Embedded guest tokens grant access to data sources reachable through their
authorized dashboards, not to SQL Lab queries or ad hoc SQL execution. Charts
cannot use a SQL Lab `query` datasource. Naming an authorized chart or dashboard
in a request does not grant a guest access to a stored query, even when the
guest role has permission to read its underlying tables. Requests to `/api/v1/explore/form_data`
and to the Explore permalink POST and GET endpoints
(`/api/v1/explore/permalink` and `/api/v1/explore/permalink/<key>`)
for an unauthorized query datasource return HTTP 403, like unauthorized dataset requests.

## Chart display names

Dashboard charts and cross-filter chips use configured column and metric display
names even when a viewer cannot access the underlying SQL dataset directly. This
also applies to embedded guests. Set a column or saved metric's verbose name in
the dataset editor, or supply a custom label in the chart editor. Fields without
a configured display name keep their original names.

For viewers without dataset access, the dashboard datasets API supplies these
names in `chart_display_labels`, keyed by chart ID and then by field or metric
identifier. Viewers with dataset access use the existing `verbose_map`; the API
omits `chart_display_labels` and skips the per-chart checks needed to generate it.
Each entry contains labels from recognized saved display controls on an accessible
chart on that dashboard. Filter-only fields, sort-only fields, expression
internals, and dataset fields absent from those controls are excluded. A background
query-context refresh cannot add labels for other fields. Table, AG Grid, and
Handlebars charts exclude controls hidden by their saved query mode; Handlebars
does not use percentage metrics. Other visualizations use the shared list of
recognized control names without checking whether their plugin renders each
control. Legacy, API-created, or imported charts can therefore retain labels for
unused saved controls, such as `all_columns` left over on a pie chart. Generated
identifiers such as `__timestamp` keep their existing fallback labels.
Guest tokens must authorize the dashboard and, when a `datasets`
allowlist is present, the SQL dataset. Semantic views do not supply this map.

Custom security managers can specialize
`can_access_dashboard_chart_labels(dashboard, chart, *, guest_dashboard_access=None, datasource_access=None)`
to restrict label access for callers without datasource access. The hook is skipped
for callers with datasource access, who receive the existing `verbose_map`; an
override of this hook cannot restrict that map. The default implementation also
honors existing `can_access_chart` and `raise_for_access` overrides and the
`EXTRA_RAISE_FOR_ACCESS_BYPASS` configuration. For the built-in security manager,
guest checks reuse the dashboard grant. Non-guest checks reuse the request's denied
datasource decision and prefetched chart editors and viewers without repeating
datasource permission queries for every chart.

## Callbacks

### `resolvePermalinkUrl`

When a user copies a permalink from an embedded dashboard, Superset generates a URL on its own domain. In an embedded context this URL is usually not meaningful to the host application's users — the dashboard is rendered inside the host app, not at the Superset URL.

The `resolvePermalinkUrl` callback lets the host app intercept permalink generation and return a URL on the host domain instead:

```javascript
embedDashboard({
  id: 'my-dashboard-uuid',
  supersetDomain: 'https://superset.example.com',
  mountPoint: document.getElementById('superset-container'),
  fetchGuestToken: () => fetchGuestToken(),
  /**
   * Called when Superset generates a permalink.
   * @param {Object} args - { key: string } — the permalink key
   * @returns {string | null} - your host URL, or null to use Superset's default
   */
  resolvePermalinkUrl: ({ key }) => {
    return `https://myapp.example.com/dashboard?permalink=${key}`;
  },
});
```

If the callback returns `null` or is not provided, Superset uses its own permalink URL as a fallback.

### Permalink origin rewriting

This rewrite only applies to the non-embedded permalink path — it has no effect on embedded dashboards. When Superset is not embedded, it rewrites the origin of any permalink URL it generates to `window.location.origin` before showing it to the user, which keeps a proxied or subdirectory-deployed Superset from handing out a permalink that points at an internal hostname the user's browser can't reach.

When Superset **is** embedded, this rewrite is skipped entirely regardless of the flag below: a `resolvePermalinkUrl` callback's return value is used as-is, and if no callback is provided (or it fails), the backend-supplied URL is also returned as-is.

If your reverse proxy correctly forwards `X-Forwarded-Host` and you'd rather non-embedded permalinks carry the backend's literal origin, opt out of the rewrite with `EMBEDDED_DISABLE_PERMALINK_ORIGIN_REWRITE`:

```python
# superset_config.py
EMBEDDED_DISABLE_PERMALINK_ORIGIN_REWRITE = True
```

This defaults to `False` (rewrite enabled) and only affects non-embedded permalinks. Flipping the default would regress the common proxied/subdirectory deployment by exposing an unreachable internal host in copied permalinks.

## Feature Flags for Embedded Mode

### `DISABLE_EMBEDDED_SUPERSET_LOGOUT`

Hides the logout button when Superset is embedded in a host application. This is useful when the host application manages the session lifecycle and you do not want users to accidentally log out of the embedded Superset session:

```python
# superset_config.py
FEATURE_FLAGS = {
    "EMBEDDED_SUPERSET": True,
    "DISABLE_EMBEDDED_SUPERSET_LOGOUT": True,
}
```

When enabled, the **Logout** menu item is removed from the user avatar dropdown in the embedded view. The session can still be invalidated server-side by revoking the guest token.

### `EMBEDDED_SUPERSET`

Must be `True` to enable the embedded SDK and the guest token endpoint. Without this flag, `embedDashboard` will fail to load.

### `EMBEDDED_CREDENTIAL_FALLBACK`

Allows a database connection that authenticates logged-in users per-user via OAuth2 to
also carry a single Snowflake username with either a password or a PEM key pair, used
**only** for embedded guest requests.

This exists because the two authentication models do not meet. An embedded viewer signs
in with a guest token rather than a Superset account, so there is no per-user OAuth2
token to resolve for them — and an external viewer may have no identity on the
analytical database at all. Without a fallback, embedded dashboards on a per-user OAuth2
connection cannot run queries.

```python
# superset_config.py
FEATURE_FLAGS = {
    "EMBEDDED_SUPERSET": True,
    "EMBEDDED_CREDENTIAL_FALLBACK": True,
}
```

With both flags on, engines that support it (currently Snowflake) show an **Embedded
guest credentials** section on the **Basic** tab of the connection dialog. The section
is editable only when the connection has an OAuth2 client and **Impersonate logged in
user** is on; otherwise it is disabled and states what is missing.

#### Before turning the flag on

Turning the flag on stops embedded dashboards on some existing connections from
loading for embedded viewers. A Snowflake connection with **Impersonate logged in
user** on but no OAuth2 client (none in its **OAuth2 client information** and no
`DATABASE_OAUTH2_CLIENTS` entry for Snowflake) served embedded viewers under its base
account, because impersonation without OAuth2 never changed the Snowflake login. With
the flag on, Superset refuses those viewers rather than serve them under an identity
nobody chose for them. The viewer sees *This chart can't be shown here because its
database connection isn't set up for embedded dashboards*, and the server log has a
`Refused an embedded viewer's query on database connection ...` warning naming the
connection and the fix. Logged-in users are not affected.

Update each such connection before turning the flag on, in one of two ways:

- **Keep serving embedded viewers under the base account:** on the **Advanced** tab,
  under **Security**, turn off **Impersonate logged in user**. On a connection with no
  OAuth2 client this changes nothing for logged-in users, who were already on the
  base account.
- **Serve embedded viewers under a dedicated account:** configure an OAuth2 client and
  **Embedded guest credentials** as described below. Logged-in users then sign in to
  Snowflake individually through OAuth2.

#### Setting up the credential

1. Enable `EMBEDDED_SUPERSET` and `EMBEDDED_CREDENTIAL_FALLBACK` (above).
2. Open the Snowflake connection for editing. On the **Basic** tab, expand **OAuth2
   client information** and enter the client ID, client secret, authorization and token
   request URIs, and scope. Alternatively, configure a deployment-wide client for
   Snowflake in `DATABASE_OAUTH2_CLIENTS`.
3. On the **Advanced** tab, under **Security**, turn on **Impersonate logged in user**.
   On a new connection this option appears only after you connect, so connect first and
   then edit the connection.
4. Back on the **Basic** tab, expand **Embedded guest credentials**, enter the Snowflake
   username, choose **Password** or **Key pair**, and fill in the secret.
5. Save. The section header shows **Configured** once a credential is stored.

Configure the Snowflake OAuth2 scopes explicitly to match your integration. For
example, `session:role:ANALYST refresh_token` selects the `ANALYST` role and requests a
refresh token. Omitting a role scope uses the user's default role; the dialog does not
prefill a scope or require a specific role scope.

For key-pair authentication, enter the Snowflake username, its PEM private key, and an
optional passphrase; register the corresponding public key with that Snowflake user. The
credential is stored encrypted in the connection's *Secure Extra* under
`embedded_credentials`. Passwords, private keys, and passphrases are masked on read,
while the username stays visible so an administrator can see which database user
embedded queries run as.

The credential must be complete: a username with no password or private key, or the
reverse, is rejected when both embedding flags are enabled. A whitespace-only username
is invalid. Validation uses the engine's credential rules and rejects malformed JSON
or non-object credential values. It checks the edited credential, so an incomplete
imported credential can be completed or cleared.

To remove the credential, expand **Embedded guest credentials**, click **Remove embedded
guest credentials** (or clear every field), and save. This deletes the
`embedded_credentials` key from *Secure Extra*. Removal stays available while the section
is otherwise disabled.

#### Requirements and limitations

- Both `EMBEDDED_SUPERSET` and `EMBEDDED_CREDENTIAL_FALLBACK` must be enabled. While
  either is off, a stored credential is preserved, unused, and does not block unrelated
  edits, but a new or changed credential is refused.
- The connection needs an OAuth2 client — per-connection **OAuth2 client information**
  or a deployment-wide `DATABASE_OAUTH2_CLIENTS` entry — and **Impersonate logged in
  user** must be on. Superset refuses to save a credential otherwise, and it never
  applies to a connection without OAuth2. A client whose ID or secret is blank counts
  as no client. While a credential is stored, turning impersonation off is refused;
  remove the credential first.
- Embedded viewers run with the embedded account's **default Snowflake role**. The
  connection's configured role and authenticator are not used for guest connections.
- The embedded account needs `USAGE` on the connection's warehouse.
- Supported secrets are a password, a Snowflake programmatic access token entered as the
  password, or a key pair (PEM private key with an optional passphrase).
- Alerts, reports, connection tests, and logged-in users never use the credential; they
  keep using the connection's own credential or their per-user OAuth2 token.
- **Async queries run logged-in users as the base account.** With
  `GLOBAL_ASYNC_QUERIES` on, guest queries use the same fallback credential as
  synchronous guest queries. Logged-in users' chart queries on a Snowflake OAuth2
  connection, however, run in the async worker under the connection's own base
  credential instead of the user's OAuth2 token, so Snowflake grants and row access
  policies keyed to the user do not apply and the queries are attributed to the base
  account. This predates `EMBEDDED_CREDENTIAL_FALLBACK`, and the flag does not change
  it. Leave `GLOBAL_ASYNC_QUERIES` off on deployments that depend on per-user OAuth2.
- **Turn on Per user caching on OAuth2 connections.** Guest results always get their
  own cache partition (below), but logged-in users do not unless **Per user caching**
  (**Advanced** → **Security**) is on, or the `CACHE_IMPERSONATION` or
  `CACHE_QUERY_BY_USER` feature flag is enabled. Without one of them, logged-in users
  share one cache entry per query, so a user can be shown a result fetched under
  another user's OAuth2 identity, including rows their own Snowflake policies would
  hide, until the entry expires.
- **Connections created in SQLAlchemy URI mode** show neither the **OAuth2 client
  information** nor the **Embedded guest credentials** section, and an existing
  connection cannot be switched to the dynamic form while editing. For such a
  connection, set `oauth2_client_info` and `embedded_credentials` directly in
  **Secure extra** (**Advanced** → **Security**), or configure a deployment-wide
  client in `DATABASE_OAUTH2_CLIENTS`.
- **Turning off Impersonate logged in user moves embedded viewers onto the base
  account.** The credential applies only while impersonation is on. With it off,
  embedded viewers query under the connection's own credential, and so do logged-in
  users, who also stop signing in through OAuth2.

Understand what this grants before enabling it:

- **Every embedded viewer of that connection queries as that one database user.** Guest
  tokens carry no database identity, so per-user attribution and any database-side
  row-level security keyed to the user do not apply. Use a dedicated account with the
  narrowest access the embedded dashboards need, and enforce per-viewer restrictions
  with Superset's own [row-level security](#security-notes) rules in the guest token.
- **Logged-in users are unaffected.** They continue to authenticate individually via
  OAuth2 and have no route to the stored credential.
- **The guest token's `username` claim is never used to connect.** Whoever mints the
  token controls that claim, so it is deliberately kept out of the connection identity.
  Connection-mutator hooks receive the selected fallback connection username.
- **An embedded viewer never silently falls back to the connection's base credential.**
  With this flag on, a guest on a connection with impersonation enabled that has no
  OAuth2 client, or no applicable credential — none configured, or one that is
  incomplete — is refused with an error rather than connected as whichever account the
  connection URL carries. The viewer is told only that the chart's connection isn't
  set up for embedded dashboards; the server log names the connection and the fix.
  Deployments that leave the flag off keep their existing behaviour.
- **Guest results are cached separately.** Queries run under the fallback credential get
  their own cache partition, distinct from every logged-in username, so an embedded
  viewer and a logged-in user never share a cached result (or, with
  `GLOBAL_ASYNC_QUERIES`, a deduplicated query task) for the same chart. Missing or incomplete credentials also receive a separate cache key, so a
  warm logged-in cache cannot bypass the missing-credential refusal.
- Turning the flag back off is a kill switch, not a deletion: the stored credential stops
  being offered and stops being used, but is preserved.

## URL Parameters

The following URL parameters can be passed through the `urlParams` option in `dashboardUiConfig` or appended to the embedded iframe URL:

| Parameter        | Values             | Effect                                                                          |
| ---------------- | ------------------ | ------------------------------------------------------------------------------- |
| `standalone`     | `0`, `1`, `2`, `3` | `0`: normal; `1`: hide nav; `2`: hide nav + title; `3`: hide nav + title + tabs |
| `show_filters`   | `0`, `1`           | Show or hide the native filter bar                                              |
| `expand_filters` | `0`, `1`           | Start with filter bar expanded or collapsed                                     |

## Embedding a Single Chart

Individual charts can also be embedded standalone, outside of a dashboard, using a chart permalink. From Explore, generate a permalink for the chart, then append URL parameters to it:

```
/explore/p/<permalink-key>/?standalone=1&show_download=1
```

| Parameter       | Values   | Effect                                                                     |
| --------------- | -------- | -------------------------------------------------------------------------- |
| `standalone`    | `0`, `1` | `0`: normal Explore view; `1`: hide the Explore header and controls        |
| `show_download` | `0`, `1` | Show a compact download control (CSV, JSON, Excel) on the standalone chart |

`show_download` is opt-in and has no effect outside of `standalone=1`. The download control still respects the viewer's export permissions — it's hidden for users who lack them even when the parameter is set. With the `GRANULAR_EXPORT_CONTROLS` feature flag enabled, this requires the `can_export_data` permission on `Superset`; otherwise it falls back to `can_csv` on `Superset`.

Explore's **Embed Code** button on a chart also generates one of these permalink URLs wrapped in an `<iframe>`, giving you a session-authenticated iframe embed. That's a separate flow from dashboard embedding above: it doesn't go through `@superset-ui/embedded-sdk`, guest tokens, or the `dashboardUiConfig` options — the viewer needs an existing Superset session with the `can read on Explore` permission, in addition to access to the chart itself. Viewing the same chart on a dashboard doesn't require that permission, so a role scoped only for dashboard viewing gets an access denial on this URL.

One caveat when the host page lives on a different site than Superset: the default `SESSION_COOKIE_SAMESITE = "Lax"` setting keeps the session cookie out of cross-site iframe requests, so the viewer lands on the login page instead of the chart. Serving both from the same site avoids this; otherwise set `SESSION_COOKIE_SAMESITE = "None"` together with `SESSION_COOKIE_SECURE = True` and allow the host origin in your `TALISMAN_CONFIG` `frame-ancestors`. Even with that configuration, browsers that block third-party cookies by default (including Safari) can still redirect the viewer to the login page. For those cases, host the iframe on the same site as Superset, or use the dashboard embedding SDK's guest-token flow above instead.

## Security Notes

- **Guest tokens expire** — their lifetime is controlled by the `GUEST_TOKEN_JWT_EXP_SECONDS` config (default: 5 minutes). Refresh tokens before they expire using a token refresh mechanism in your host app.
- **Datasource scope** — chart and native-filter access is bound to both the datasource type and its identifier. Legacy native-filter targets without a type refer to SQL datasets. When the optional guest-token `datasets` allowlist is present, only the listed SQL datasets are reachable and semantic views are denied.
- **Row-level security** — pass `rls` rules in the guest token request to restrict which rows are visible to the embedded user. Semantic views cannot enforce guest-token SQL clauses, so queries and cached-result reads are rejected when a global rule or a rule scoped to the semantic view applies. For hosts, a global guest rule deliberately refuses every semantic view, and a dataset-scoped rule can also refuse a semantic view even when the rule was intended for a SQL dataset. Read permissions do not override these restrictions. Semantic views remain accessible when no guest rule applies; SQL datasets continue to enforce their applicable rules.
- **Allowed domains** — restrict which host origins can embed a dashboard by setting **Allowed Domains** per-dashboard in the _Embed_ settings modal. Superset checks the request's `Referer` header against this list before serving the embedded view; an empty list allows any origin, so configure this explicitly for production.
- **Redacted errors** — API responses to a guest token report a generic `An error occurred while fetching the data.` instead of the underlying error, since engine errors quote catalog, schema, table and column names. Errors Superset raises itself — access denials, timeouts, payload validation — keep their message, and the full error is always available in the server logs.
- **OAuth2 connections and guests** — a guest cannot complete an OAuth2 authorization, so Superset does not start one for them, and an embedded viewer on an OAuth2 connection with no applicable credential is never sent into a login flow they cannot finish. With `EMBEDDED_CREDENTIAL_FALLBACK` off, the connection attempt fails with the database driver's authentication error, and the viewer sees the generic `An error occurred while fetching the data.` message. With it on, Superset refuses the query before connecting, and the viewer sees a message saying the chart's database connection isn't set up for embedded dashboards, without naming the connection. Either way the reason is in the server logs. To serve embedded dashboards from such a connection, see [`EMBEDDED_CREDENTIAL_FALLBACK`](#embedded_credential_fallback).


## Guest-token request-header size diagnostics

A successful guest-token mint does not guarantee the token can pass through your
deployment's proxies. Limits apply to the **encoded JWT bytes plus header
overhead**, not the number of RLS rules or identifiers. A proxy can reject the
subsequent authentication request before it reaches Superset, including an HTTP
400 HTML response instead of JSON. A 400 alone does not establish a size problem.

Operators can set a deployment-specific diagnostic budget in `superset_config.py`:

```python
# Example only: choose a budget for your complete proxy path.
GUEST_TOKEN_HEADER_MAX_BYTES = 16 * 1024
```

The default is `None` (no budget warnings). Positive integer budgets count UTF-8
bytes of `GUEST_TOKEN_HEADER_NAME`, `: `, the encoded token, and `\r\n`
(four framing bytes). Only sizes **strictly greater** than the budget warn;
equality does not. This is consistent diagnostic accounting, not a prediction of
every proxy's wire-level accounting, HTTP/2 compression, or total-header limits.
Leave a safety margin and validate your actual deployment, including custom
header names. Zero, negative, non-integral, or non-numeric values (including strings and
booleans) disable budget warnings, as do values above JavaScript's maximum safe
integer (2^53 − 1). Whole-number floats are accepted. Convert environment-variable
strings to integers in deployment configuration to enable the budget.

Issuance audit metadata includes `token_bytes`, `header_bytes`,
`header_budget_bytes`, and `header_budget_exceeded`. Issuance remains HTTP 200
with the same token and response shape. The embedded bootstrap exposes the budget
and configured header name; reload the iframe after changing deployment config.
The embedded client measures initial and refreshed tokens and warns in the
developer console with sizes only. Initial authentication failures get a targeted
suggestion only when the request's token exceeds the budget and the failure has
no status or HTTP 400/431/494; other statuses and ambiguous in-flight
refreshes use the generic error. Refresh warnings do not restart authentication.
These diagnostics do not record JWTs, decoded claims, RLS SQL, or request headers.

[AWS Application Load Balancer quotas](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-limits.html)
list a non-adjustable 16 K single-header limit. Increasing a Superset diagnostic
budget does not increase that limit or add large-token support.

To reduce payload size, replace large inline RLS ID lists with a compact
entitlements-table subquery where supported by your database. Keep the same
tenant/user restrictions, derive identity from your trusted token-issuing
backend, and verify equivalent row access and query performance before rollout.
Do not remove RLS or broaden entitlements to make a token smaller.

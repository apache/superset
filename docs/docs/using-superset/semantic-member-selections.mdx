# Semantic member selection versions

Semantic providers can declare `selection_identity_version` when changing their
member identity encoding. Cube's stable-member-ID adapter requires
`cube-member-id-v1`. Deploy the compatible core library, host, frontend and Cube
adapter together; do not roll back to title-keyed code after saving ID-based charts.

Saved Cube selections without this version are rejected, even when a saved title
happens to equal a member ID. No historical title mapping is recovered. Open each
chart in Explore, choose **Start field selection**, reselect its metrics,
dimensions, filters and sorting, then save. Reset also clears field-dependent
formatting; it does not overwrite the saved chart until Save is chosen. Native
filters and chart customizations have a separate reset in their configuration
form that clears fields, pre-filters, sorting, defaults and dependencies.

Dashboard filters retain their own saved generation. Old filter state and
unversioned external member overrides cannot borrow a chart's version. Recreate
old dashboard permalink/filter state after reselection. Cross-view overlays are
rejected unless their source identity matches the receiving semantic view;
matching display titles are not proof of matching members.

The marker is a compatibility contract, not an authorization credential. API
clients must rebuild their selections from current member IDs before supplying
`extras.semantic_selection_version` on each query. Providers without a required
version retain their existing behavior. No metadata-database migration or
automatic rewrite of saved charts is performed.

Programmatic clients must explicitly select current member IDs. Chart-data API
queries send `extras.semantic_selection_version`; name-based datasource queries
and MCP `get_table` requests send top-level `semantic_selection_version`.
Discover the value from datasource metadata (or each external metric returned by
MCP `list_metrics`). The server never adds a missing marker from metadata.
Explore query controls remain unavailable until explicit field initialization,
so legacy filter subjects cannot trigger value suggestions before reselection.

Custom SQL `WHERE` and `HAVING` clauses are not supported on semantic views.
Remove those clauses or use semantic dimension filters instead. Chart-data API
requests with these clauses return HTTP 400 before querying the provider.

Filter-value suggestions and Matrixify **Members** and alphabetically sorted
**All** modes use the identity version stored with the chart's selections. After
**Start field selection** and explicit reselection, these controls can load
suggested values. Old selections cannot borrow the version from freshly fetched
datasource metadata, even when an old title exactly matches a current member ID.

If provenance is missing or stale, suggestions remain unavailable and saved values
are preserved. Enter values manually in the filter or Matrixify **Members** mode,
or reset and reselect the fields to restore suggestions.

The column-values API accepts `semantic_selection_version` as a query parameter.
Missing or stale versions on versioned views return an empty `result` and
`suggestions_status: "unavailable_versioned_view"` before reading cached values
or requesting provider values. A matching version enables the existing retrieval
and search behavior. Tables and unversioned views keep their existing behavior.

The version is recorded once per chart, not per filter. A filter column added by
editing saved form data directly inherits the chart's version, so suggestions are
a usability aid for compatible selections, not a guarantee about each filter's
provenance. The marker is not an authorization check; access to the datasource is
verified separately.

## Time comparison

Time comparison is not yet supported on semantic views. Remove the time shift
from the chart or dashboard comparison control to run the query. This includes
relative shifts, inherited ranges, and custom start dates, even for aggregate-only
charts. The host refuses these queries before reading cached chart results to
avoid showing incorrect comparison values. SQL dataset comparisons and semantic
queries without time shifts are unaffected.

## Resampling of dates

Semantic views can resample a DATE axis, for example to fill daily gaps between
observations. DATE series labels, raw results and exports without resampling keep their
date-only representation. Resampled results use the same datetime representation
as ordinary dataset time-series charts: CSV shows calendar dates for daily
buckets, while XLSX cells include the midnight time component.

As with ordinary datasets, a NULL time-axis bucket cannot be resampled; filter out
NULL dates before applying resampling. Resampling does not enable time comparison
on semantic views. Forecasting on a DATE axis is not addressed by this conversion.

## Clearing dashboard filters

**Clear all** stages empty values for in-scope filters; **Apply** commits the
clear. Cleared semantic filters remain usable without a reselection warning,
including filters that had no selected value. Saved defaults stay cleared while
the cleared state is carried in the session, filter-state key, or permalink; a
fresh dashboard load without that state restores the defaults. Required filters
still need a value before Apply is enabled. Clear all also discards stale values
for in-scope filters and dismisses their reselection warning. The discarded
predicates are not applied to charts; the previously applied state remains until
Apply. To use legacy selections again, reset and explicitly reselect them.

## Native filter columns

The native-filter column picker lists each semantic member name once, even when
the provider exposes several time-grain variants of that member. This matches
Explore's column list: choosing a filter column selects the member, not a grain
variant. Distinct member names remain separate choices.

The **Drill by** menu also lists each dimension once, using its display label
when the provider supplies one. Selecting it still drills by the member name.
The Column, Time column, and Pre-filter pickers in semantic-view native-filter
settings show these labels. When labels repeat, the member ID appears on a
separate line in each choice and in the selected value. The Explore Filters
subject picker shows the same qualified choices and selected subject; its
compact saved-filter pill still uses the unqualified label. Searching by member
ID still finds the choice. Labels also appear in display-control column lists
and Drill by result labels.

## Choosing a datasource for a new chart

The chart-creation datasource picker, including when opened from a dashboard,
identifies each semantic view by its name and a **Semantic View** marker. These
labels are also available to screen readers; internal datasource IDs are not the
option names.

## Dynamic group by display controls

Dynamic group by display controls are available for ordinary datasets, not
semantic views. On a dashboard with only semantic views, the control is absent
from the add menu. On a mixed dashboard, its datasource picker lists ordinary
datasets only. Previously saved controls targeting semantic views remain in the
dashboard configuration, but are hidden from viewers and do not change chart
requests. In the editor, such a control shows a notice and can only be removed.

## NULL filter values

For semantic views, a selected NULL value means a missing value, rather than SQL's
unknown comparison result. Equality to NULL and `IN (NULL)` use `IS NULL`;
inequality to NULL and `NOT IN (NULL)` use `IS NOT NULL`.

A mixed selection such as `IN ('a', NULL)` means `IN ('a') OR IS NULL`. Its negative
form, `NOT IN ('a', NULL)`, means `NOT IN ('a') AND IS NOT NULL`; it excludes both
`'a'` and missing values. An empty IN selection matches no rows and an empty
NOT IN selection matches every row, including missing values, as in SQL. A total
without grouping still returns one row, for example a count of 0.

Chart and dashboard exclude (`NOT IN`), not-equal (`!=`), `NOT LIKE` and `NOT ILIKE`
filters keep rows with missing values, matching ordinary datasets. For example,
`NOT IN ('a')` becomes `NOT IN ('a') OR IS NULL`. Select NULL explicitly to
exclude those rows too; `!= NULL` remains `IS NOT NULL`.
This user-filter normalization does not change SDK-authored predicates or
literal SQL semantics. A provider that does not support an operator continues
to refuse it as before.
Cached chart results for semantic views and ordinary dataset charts with annotation layers are rebuilt once after deployment.

Host filter-value types accept missing values (`None`) inside list selections
and variable-length tuples, so multi-value selections can preserve NULL members.

Every semantic provider must support mixed positive selections and NULL-preserving
exclusions through grouped OR predicates. NULL-only and mixed negative selections use ordinary leaf
predicates. Provider adapters must be upgraded before, or together with, the
host/SDK so that mixed selections preserve missing-value rows.

For adapter authors, see the [semantic filter contract](/developer-docs/extensions/extension-points/semantic-layers#filter-expressions).

## Numerical range filters

For semantic views, numerical range filters use **Minimum value** and
**Maximum value** inputs instead of a slider. No query is sent to discover
bounds. Leave either input empty for an unbounded end; leave both empty to
remove the constraint unless **Filter value is required** is enabled.
The minimum cannot exceed the maximum. Negative values and decimals are
supported, and existing minimum, maximum, and exact single-value modes remain
available. SQL dataset filters retain their discovered bounds and slider options.

# Asset approval closure plan

Written 2026-11-02, against `REPORT-2026-11-02.md`,
`REGRESSION-2026-11-02.md`, `DECISIONS-2026-11-02.md` and
`ARCHITECTURE-2026-11-02.md`. It supersedes `.local/QA-CONCLUSIONS.md` and
`.local/PA-TRIAGE.md` wherever they disagree with it.

This document closes the epic. It states the scope, the exit test, the
remaining work with owners, and the one letter that has to go to VISA. It is
not a status report and it does not leave questions open. Where the four
source documents disagree, it picks one and says why.

Target dates: our remaining work lands by **Friday 13 November 2026**, VISA's
answers are due the same day, and QA signs off on **Monday 16 November 2026**.

---

## 1. Where this stands

The engineering is done. Every one of the 45 tracker rows that describes
product behaviour is fixed and was verified by hand in the browser across
eleven walks, as were twelve further defects (NEW-1 to NEW-12) that were found
in those walks and never put on the tracker. The four rows still open, S-05,
S-06, S-07 and S-09, are not missing code: each has working code behind a
documented default, and each is waiting on somebody to write a choice down.
The epic has not closed because nobody ever wrote down what closing means, so
every QA run has been a discovery run rather than a re-test, and a queue that
discovers at the rate it fixes never drains. Four rows were also marked Fixed
while still broken, which cost roughly an iteration each, and that is why a
passing test suite is not treated as evidence anywhere in this document.

## 2. The scope line

This is the section that matters. Everything below is in V1 or it is not in
V1, by name. Nothing is in neither.

### 2.1 In V1

The control, as built and walked:

1. A write to a published dashboard, chart or dataset by an editor is captured
   as a change request, not applied.
2. A second editor of that same asset, who is not the author, approves it, and
   only then does it apply.
3. There is no administrator bypass, at the object layer or anywhere else.
4. Captured operations include saves, deletes, restores, native filter
   configuration, embedded configuration, the publish transition, and MCP
   writes.
5. Viewers see nothing: no banner, no pending tag, no Edit button, no review
   controls, through the interface and through the API.
6. With the feature flag on and the gate not installed, writes are refused
   rather than applied.
7. With the feature flag off, the surfaces disappear and the enabled endpoint
   says so.
8. Approving a change whose asset moved underneath it is refused, naming the
   field that moved.
9. Exemptions, as built: editors list, dataset description, a certification
   only `extra` write, a column resync that only re-reads types the source
   itself reports, an unpublished dashboard, and a save that changes nothing.
   A save that mixes an exempt change with a governed one is governed.
10. The approval is recorded with its author, its reviewer, its decision time
    and its payload, and that record is kept indefinitely.
11. Approving an import that would overwrite an existing asset is refused with
    a message that says what to do instead. An import that only creates new
    assets is unaffected, including through `superset import-dashboards`.
12. Approval is a permission of its own, `can_approve`, enforced on the route
    and not only in the interface, configurable through
    `ASSET_APPROVAL_APPROVER_ROLES`, with service and integration accounts
    excluded through `ASSET_APPROVAL_MACHINE_USER_ROLES`.

Plus the nine remaining pieces of work in section 4.1. Nothing else enters V1.

### 2.4 The rule that keeps the line closed

From the moment VISA signs section 2, V1 scope is frozen. **Only a control
failure reopens it.** Nothing else does: not a copy fault, not a dead end, not
a missing toast, not an ergonomics finding, not a better idea.

For this feature, a control failure is exactly one of the following five
things, and nothing else:

1. **Unreviewed content reaches a viewer.** A write to a published dashboard,
   chart or dataset applies to the live asset without an approved change
   request, through any interface: the browser, the REST API, MCP, the CLI, or
   an import.
2. **The second pair of eyes is not a second pair of eyes.** A change is
   approved by its own author, or by somebody who is not a current editor of
   that specific asset, including by an administrator who is not an editor.
3. **The gate is absent while the feature reports itself enabled.** Any write
   path that can mutate one of the three asset types is reachable without the
   gate while the feature flag is on and the extension is loaded.
4. **What applies is not what was approved.** An approval publishes content
   other than what the approver was shown, or publishes over a version that
   moved after the change was captured without refusing, or applies twice.
5. **The record is wrong.** The approval record names the wrong author or the
   wrong reviewer, omits one of them, or is absent for a change that applied.

Three conditions on a reopen, all of them required:

- It is reproducible from a freshly seeded demo, through the interface a person
  would use, with the repro written down. A finding supported only by a
  screenshot, a log line or a reading of the code is not yet a reopen.
- It is raised against one of the five numbered items above, by number.
- The named closure owner accepts it. Anybody may report; one person reopens.

Everything that is not a control failure is a V2 ticket. It is recorded, it is
sized, and it does not reopen V1, however cheap it looks. A finding that is
cheap to fix and not a control failure is still a finding that restarts the
queue, and restarting the queue is what this epic has done nine times.

### 4.4 The caveats that must appear in the sign-off note verbatim

Each is acceptable to ship. None is acceptable to ship silently.

- Approver roles are at the stock default and VISA owns narrowing them.
- The service-account role list is empty and VISA owns populating it.
- The author's written rationale is on the change request and visible in
  review, and is not surfaced in the asset's version history panel.
- After approving a delete from the asset's own page the reviewer lands on a
  dead page. The delete itself applied correctly.
- Restoring an archived asset gives no on-screen feedback.
- Approved content can arrive late in an already-open browser. Unapproved
  content is never shown.
- At a first publish the approver reviews the exposure, not the content.
- The durable approval record is the change request table and is kept
  indefinitely. The readable summary in an asset's history panel prunes at 30
  days unless the retention window is set at deployment.
- An administrator who is not an editor can author an embedded configuration
  change that nobody can approve. This is the no-bypass rule working.
- A native filter save refused for a conflicting draft closes the modal, so
  the author retypes the filter name.
- The approver learns that an author has lost edit access from the refusal
  rather than in advance. This is the open half of QA-07, not a new defect.
- Removing yourself from an asset's editors is accepted and ignored. Core
  behaviour, filed upstream. Adding an editor, which the no-approver flow
  depends on, works and was verified.
- QA-08 and QA-09 rest on unit tests. No two-session race was reproduced.
- 45 tracker rows plus 12 defects found and fixed in manual passes, all
  verified by hand. 45 was not the whole story.

## 6. How this does not happen again

Four changes. They are aimed at the two things that actually went wrong: four
rows read Fixed while broken, and the queue never drained.

1. **A row is marked Fixed only by somebody who did the thing through the
   interface a person uses, and the row carries that evidence.** Not the
   commit, not the test name. The four false Fixed rows were each written,
   reviewed and unit-tested, and each was caught only by using the feature.
   This is the one guard with a measured hit rate on this epic.

2. **A change to gate behaviour is reviewable only if its test issues a
   request rather than calling a function.** All four failures put the fix on
   the path the test exercised while the product used another. A test that
   calls a predicate directly answers a narrower question than a reviewer
   reads it as answering, so for an exemption or a refusal, a test that does
   not send a request is a blocking review comment.

3. **A QA run is either a re-test of named rows or an exploratory pass, never
   both.** A re-test run takes a written list and reports pass or fail on each
   row and nothing else. Anything it notices in passing goes into the next
   exploratory batch, not into the current queue. Discovery and fixing at the
   same rate is what kept this queue alive for nine iterations, and the fix is
   to stop letting one run feed itself.

4. **Every epic gets a named closure owner, and it is not the person
   fixing.** The closure owner owns the exit checklist, is the only person who
   can reopen frozen scope, and is measured on the epic closing rather than on
   the queue emptying. "QA has no open findings" is not an exit test, because
   no software passes it. Section 3 is an exit test, because it is finite.

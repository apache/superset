# Asset approval — manual QA pass, 2026-11-02

Run against `make asset-demo` on `docker-compose-light.yml`, in the browser,
as each of the four seeded accounts in turn: `alex` (author), `priya`
(approver), `sam` (viewer, editor of nothing), `morgan` (Admin, editor of
nothing). Every result below was reached through the UI, not the API, except
where it says otherwise.

## What this pass was for

The tracker's nine open rows had fixes written for them but none had been
exercised by hand. Three turned out not to work, and walking the flow turned
up eleven defects nobody had filed — one of them the cause of a tracker row
that had been diagnosed as something else. A second pass then walked the six
areas the first had left alone; it found a twelfth, and reversed a row that
had been reported fixed a week earlier.

### R4-08 is still open, and why the obvious fix is wrong

The filter modal marks a filter modified the moment its form is touched and
never un-marks it, so opening a filter, editing a field and putting it back
still posts it and creates an empty draft that locks the dashboard.

The server-side check added for this row is right to refuse: the modal
re-posts the filter in the client's canonical form, which adds nested keys
the stored configuration never carried — `controlValues.creatable`,
`controlValues.operatorType`, `targets[].datasourceType`. At the top level
nothing is added; the differences are all nested.

A rule of "ignore keys the stored side lacks" would be worse than the bug.
`controlValues.creatable` is the **Allow creation of new values** checkbox,
and a filter saved before that key existed would have the author's first
change to it dropped from the payload entirely — lost, not merely ungated.

Two routes would work, neither of them small:

1. Compare the form's values against the values it was seeded with. Both go
   through `transformFormInput`, so it is like for like. Needs the modal to
   keep that snapshot, which it does not today.
2. Put both sides through `transformFormInput` before comparing.

A comparison in `useModalSaveLogic` was tried and reverted: it compared
`transformFormInput` output against `transformSavedFilter` output, which are
different shapes, so it never fired.

### NEW-4 is the one worth reading twice

priya opened the dataset editor, **changed nothing**, pressed Save, and was
refused: *"Alex Rivera already has changes open on this dataset."* A save
that edited nothing was being treated as a governed change.

One cause, four symptoms:

1. **R4-06**: certifying a dataset was never exempt in the UI, because the
   echo dragged `columns` and `metrics` along with it. The exemption itself
   was correct — a certification-only `extra` PUT through the API applies
   with another author's change open.
2. The 129076 empty-save bug was still live for datasets.
3. A reviewer's **What changed** always led with columns and metrics,
   whatever the author had really edited.
4. An author could not make an exempt-only dataset edit at all.

`None`, `""`, `"{}"`, `{}` and `[]` are now one statement about a field that
holds nothing — only when **both** sides are empty, so emptying a field that
held something is still a change.

## What held up

- **The viewer sees nothing.** With a change awaiting review, `sam` sees the
  live title, no banner, no "Changes pending" tag on the chart that has one,
  no Edit button, no review controls. The feature's central claim holds.
- **An administrator has no bypass.** `morgan` is Admin and an editor of
  nothing: the Approvals queue says nothing needs them, the bell has no
  badge, and renaming a chart `alex` holds is refused with the same lock
  anyone else gets.
- **The happy path.** Request review names the approver; the bell counts;
  Approve publishes; the request is recorded `approved` with its reviewer and
  decision time and the asset's slot is freed.
- **The dataset round trip.** Edit → captured → submitted → reviewed on a
  real diff → approved → applied. The metric and the column label are live.
- **No approver.** The dialog says so and offers the Editors picker inline,
  with "Changing editors doesn't need approval."
- **Stale review.** Approving a request that moved underneath is refused,
  says why, and the panel re-reads itself to the new version.

- **Delete is captured, not applied.** Archiving a chart answers 202 and the
  chart stays in the list; nothing is removed until the delete is approved.

## Second pass: the six areas the first left alone

### Version history (QA-16) — passes

A full cycle, author to approver: the replayed save is credited to Alex
Rivera and labelled "Approved by Priya Shah", with the review note on the
entry. Worth knowing for anyone retesting it: an approval whose replay turns
out to be a no-op writes no history entry at all, so the first attempt looked
like a failure when it was an empty change.

### The published-asset exemption (QA-18) — passes both ways

A save on an unpublished dashboard applies straight through (200). The same
asset once published is governed, and the transition is picked up without a
restart. A brand-new dashboard states the exemption correctly on screen.

### The MCP write paths (S-02, QA-13) — gated

Exercised as real tool calls against the running instance, not through the
HTTP API.

- `update_dashboard` created a change request and left the live title
  untouched.
- The capture comes back as a success, not an error (QA-13).
- `manage_dashboard_markdown`, the one that writes `position_json`, folded
  into the author's existing draft and left the layout untouched.

MCP resolves its own user before the gate is reached, so the auth source has
to be set for a scripted call; `g.user` alone is not enough.

### Embedded configuration (QA-26) — passes, with one thing worth saying out loud

The embed write is captured (202), not applied, and approving it commits the
whole thing atomically: uuid, allowed domain and `changed_by` all land. Both
editors are offered as approvers for an admin's change.

The finding is on the way there. An Admin who is **not** an editor of the
dashboard can create the change and then never get it approved: the approval
is refused 409, and the message says why. That is the lock working as
designed, not a bug, but it is the one path where an admin can reach a dead
end, and it is worth a line in the runbook.

### Restore / unarchive (R3-01) — was not fixed; now fixed

The one real regression this pass. Full detail in NEW-12 above. In short, a
restore request existed, was open, and was authored by the person looking at
it, and no read would return it; after that was fixed, the **Review** button
sent the approver to the archived chart's own page, which no longer loads.
Both halves are fixed, with a test pinning the first, and the loop is
verified end to end: approve returns 200 and the chart is back in the list.

One smaller thing seen alongside it: the restore click gives no feedback at
all, so it invites being clicked again.

### Import refusal (S-06) — passes both halves

Re-importing an exported dashboard over itself is refused 422:

> Importing over an existing dashboard needs review, which imports do not
> support yet. Import without overwriting, or ask an administrator to turn
> review off for this import.

A bundle of entirely new assets still imports, including through
`superset import-dashboards`, which hardcodes `overwrite=True`: the dashboard
was created and no change request was captured. That second half is the
regression the refusal could easily have caused, so it is the one to keep a
test on.

## Not covered

The chart Explore save path. It is exercised by the unit suites but was not
walked by hand in either pass.

# Asset approval — manual QA pass, 2026-11-02

Run against `make asset-demo` on `docker-compose-light.yml`, in the browser,
as each of the four seeded accounts in turn: `alex` (author), `priya`
(approver), `sam` (viewer, editor of nothing), `morgan` (Admin, editor of
nothing). Every result below was reached through the UI, not the API, except
where it says otherwise.

## What this pass was for

The tracker's nine open rows had fixes written for them but none had been
exercised by hand. Three turned out not to work, and walking the flow turned
up eleven defects nobody had filed — one of them the cause of a tracker row
that had been diagnosed as something else. A second pass then walked the six
areas the first had left alone; it found a twelfth, and reversed a row that
had been reported fixed a week earlier. A third pass closed everything still
open that is ours to close, and reversed another row the same way.

Where it stands after all three: every engineering item is fixed and
verified by hand. Four rows remain open and none of them is a gap in the
build — S-05 and S-07 need VISA's role lists, S-06 needs the written §5.1
disposition, and S-09 is a branch-target decision. Each has working code
behind a documented default.

### R4-08 is still open, and why the obvious fix is wrong

The filter modal marks a filter modified the moment its form is touched and
never un-marks it, so opening a filter, editing a field and putting it back
still posts it and creates an empty draft that locks the dashboard.

The server-side check added for this row is right to refuse: the modal
re-posts the filter in the client's canonical form, which adds nested keys
the stored configuration never carried — `controlValues.creatable`,
`controlValues.operatorType`, `targets[].datasourceType`. At the top level
nothing is added; the differences are all nested.

A rule of "ignore keys the stored side lacks" would be worse than the bug.
`controlValues.creatable` is the **Allow creation of new values** checkbox,
and a filter saved before that key existed would have the author's first
change to it dropped from the payload entirely — lost, not merely ungated.

Two routes would work, neither of them small:

1. Compare the form's values against the values it was seeded with. Both go
   through `transformFormInput`, so it is like for like. Needs the modal to
   keep that snapshot, which it does not today.
2. Put both sides through `transformFormInput` before comparing.

A comparison in `useModalSaveLogic` was tried and reverted: it compared
`transformFormInput` output against `transformSavedFilter` output, which are
different shapes, so it never fired.

### NEW-4 is the one worth reading twice

priya opened the dataset editor, **changed nothing**, pressed Save, and was
refused: *"Alex Rivera already has changes open on this dataset."* A save
that edited nothing was being treated as a governed change.

One cause, four symptoms:

1. **R4-06**: certifying a dataset was never exempt in the UI, because the
   echo dragged `columns` and `metrics` along with it. The exemption itself
   was correct — a certification-only `extra` PUT through the API applies
   with another author's change open.
2. The 129076 empty-save bug was still live for datasets.
3. A reviewer's **What changed** always led with columns and metrics,
   whatever the author had really edited.
4. An author could not make an exempt-only dataset edit at all.

`None`, `""`, `"{}"`, `{}` and `[]` are now one statement about a field that
holds nothing — only when **both** sides are empty, so emptying a field that
held something is still a change.

## What held up

- **The viewer sees nothing.** With a change awaiting review, `sam` sees the
  live title, no banner, no "Changes pending" tag on the chart that has one,
  no Edit button, no review controls. The feature's central claim holds.
- **An administrator has no bypass.** `morgan` is Admin and an editor of
  nothing: the Approvals queue says nothing needs them, the bell has no
  badge, and renaming a chart `alex` holds is refused with the same lock
  anyone else gets.
- **The happy path.** Request review names the approver; the bell counts;
  Approve publishes; the request is recorded `approved` with its reviewer and
  decision time and the asset's slot is freed.
- **The dataset round trip.** Edit → captured → submitted → reviewed on a
  real diff → approved → applied. The metric and the column label are live.
- **No approver.** The dialog says so and offers the Editors picker inline,
  with "Changing editors doesn't need approval."
- **Stale review.** Approving a request that moved underneath is refused,
  says why, and the panel re-reads itself to the new version.

- **Delete is captured, not applied.** Archiving a chart answers 202 and the
  chart stays in the list; nothing is removed until the delete is approved.

A save on an unpublished dashboard applies straight through (200). The same

### The MCP write paths (S-02, QA-13) — gated

- The capture comes back as a success, not an error (QA-13).

### Embedded configuration (QA-26) — passes, with one thing worth saying out loud

The embed write is captured (202), not applied, and approving it commits the

The finding is on the way there. An Admin who is **not** an editor of the
dashboard can create the change and then never get it approved: the approval

### Restore / unarchive (R3-01) — was not fixed; now fixed

The one real regression this pass. Full detail in NEW-12 above. In short, a
restore request existed, was open, and was authored by the person looking at

One smaller thing seen alongside it: the restore click gives no feedback at

### Import refusal (S-06) — passes both halves

Re-importing an exported dashboard over itself is refused 422:

A bundle of entirely new assets still imports, including through

## Third pass: closing the remaining rows

Everything left open after the second pass, taken one at a time.

### R4-08 is fixed, on the third attempt

The modal marks an item modified the moment its form is touched and never
un-marks it, so opening a filter, changing a field and putting it back still
posted that filter and opened a request.

Comparing the form against the stored filter never works: a stored filter is
saved through `transformSavedFilter` and the form through
`transformFormInput`, and the latter fills in the defaults of controls the
stored filter predates. On this dashboard that was
`controlValues.creatable`, `controlValues.operatorType` and
`targets[].datasourceType` -- three keys the stored side had never carried,
each holding the control's own default. The two shapes never match. Both
sides have to come from the form.

Two things had to be right about *when* the form is read, and each was
wrong once:

1. **Not too early.** Reading it from the modal when the panel mounts gives
   `targets: [{}]`, because a filter's dataset and column arrive from a
   fetch -- and that fetch settling re-renders the filter's form, not the
   modal around it, so the modal never sees the settled value. The form
   reports its own value instead.
2. **Not too late.** Freezing the baseline when the item is *marked*
   modified is half a second late: the filter name input debounces, so the
   form already holds the new name while the item is still unmarked, and
   the baseline was refreshed to the edit, which dropped the rename from
   the save. Antd's touched flag moves with the keystroke and is only set
   by a person typing, so that is what it freezes on.

Caught by `FiltersConfigModal`'s own "modifies the name of a filter" test,
which is the reason to run a feature's existing tests and not only the new
ones.

Verified in the browser both ways: tick a checkbox and untick it, then save,
and no request is created; rename the same filter and one is, carrying that
filter alone.

### S-04 is a half fix, and the half that was missing is the one people use

Not on the list for this pass -- it reads **Fixed (run 4)** -- and found
while trying to reproduce NEW-7.

The exemption was put on `RefreshDatasetCommand`, the dedicated refresh
endpoint. "Sync columns from source" in the dataset editor does not call it:
it reads the source's columns into the open dialog, and the author's Save
then carries them through the ordinary governed PUT. On this demo that
flipped four columns from VARCHAR to TEXT and opened a change request.

Fixed on the same SOW 5.2 grounds as the endpoint -- it does not author a
change, it re-reads what the database already says -- and deliberately
narrowly. The column set has to be unchanged, every field other than `type`
has to match what is stored, at least one type has to have moved, and every
moved type has to be the one the source itself reports. A column added or
dropped, a verbose name, a flag, a metric: all authored, all still governed,
and in all of those the source is never consulted at all. An unreachable
source answers "not a resync", so it fails closed.

### NEW-2 took the decision rather than leaving it

After a captured save the header and the browser tab kept the author's
proposed title while the banner beside them said the author and viewers were
both on the live version. Settled the way QA-19 was settled: show the live
version and say so. The proposal is still one click away under **Show
changes** and **What changed**, and the change request keeps it.

Two things the host has to get right, both found by testing rather than by
reading: the layout reducer only lets tracked actions through, so
`dashboardTitleChanged` does nothing at all and it has to be
`updateDashboardTitle`; and that action marks the dashboard unsaved, which
brought back the `beforeunload` warning NEW-1 had removed.

### NEW-6 was filed as the wrong thing

Filed as "a viewer who types the URL gets the Approvals shell". The page is
legitimately a Gamma's -- a Gamma can create charts and so can have changes
of their own. What is not legitimate is the role beneath it: with
`PUBLIC_ROLE_LIKE` set, which is Superset's documented way to let signed-out
visitors see dashboards, the anonymous role holds `can_write` on
ChangeRequest, and both grants in the entrypoint hand rights to "whoever
already holds X". So the anonymous role was seeded the approval right and
handed the Approvals page.

Nothing could be approved with it -- the route needs a user id and a strict
editorship, and `can_approve` refuses a guest outright -- but an approval
permission sitting on the anonymous role is the wrong answer to give a
control review. The seed only runs while nobody holds the right, so skipping
it from now on would have fixed new installs and left existing ones exactly
as they were; an install-time revoke makes it reach them.

### S-05 and S-07 are built; their rows are open for a reason we cannot close

Both are implemented, enforced on the route and not only in the dropdown,
and covered by tests (`test_approval_is_a_separate_permission`,
`test_machine_users_are_not_approvers`). `ASSET_APPROVAL_APPROVER_ROLES` and
`ASSET_APPROVAL_MACHINE_USER_ROLES` are how an instance says who approves
and which roles are service accounts. The rows stay open because the lists
are VISA's to write, not because anything is missing here.

### S-06's message named a control that does not exist

The refusal told the reader to "ask an administrator to turn review off for
this import". There is no such switch: the Change review page is read-only,
and the feature flag behind it is global and needs a restart, so it is
neither per-import nor anything an administrator can reach. It now says what
they can do instead, and says that an import which only creates new assets
is unaffected.

## The pattern worth naming before sign-off

Four rows in this epic have read **Fixed** while the behaviour they describe
was still there: S-01, R3-01, R4-06 and now S-04. Every one of them was
written, reviewed and unit-tested, and every one was caught only by using
the feature.

They fail the same way. The fix is put on the path the test exercises, and
the product uses a different one. S-01's patch never reached the route
because FAB had already captured the bound method. R3-01's visibility fix
was real and the Review button still navigated to a dead page. S-04's
exemption is on the refresh endpoint and the editor's button does not call
it. A test that stands next to the fix will pass in all four cases.

The cheap guard is the one that caught S-04: before marking a row fixed,
do the thing a person would do, through the interface they would use.

SIP-212: Browser-Print PDF Dashboard Reports

Branch: feature/sip-212-implementation  |  Complete implementation record — all files, roadblocks, compromises, and path to final implementation

1. What This Feature Does (How It Works End-to-End)

The existing Superset report pipeline generates PDF dashboards by taking a series of raster screenshots (Playwright/Selenium PNG captures), then stitching those PNGs into a PDF. The result is a pixelated image PDF: text is not selectable, charts are not vector, and the layout can break across tiles.

SIP-212 introduces a parallel path that uses Playwright's native page.pdf() — the same API a browser uses when you press Ctrl+P. This produces a real vector PDF with selectable text, crisp SVG charts, and correct pagination, with zero changes to the existing screenshot path.

Full Request Flow

1. Celery worker triggers report — execute.py :: _get_pdf() is called
↓
2. Feature flag check — if DASHBOARD_REPORTS_BROWSER_PRINT_PDF=True AND this is a dashboard report (not chart), call _get_browser_print_pdf()
↓
3. Build URL — DashboardPrintScreenshot.__init__() calls DashboardScreenshot.__init__() (adds ?standalone=3), then appends &print=1 via modify_url_query()
↓
4. Playwright opens URL — WebDriverPlaywright.get_print_pdf() navigates to the URL with cookie auth, waits for .standalone to appear
↓
5. Frontend detects ?print=1 — DashboardBuilder.tsx adds body.print-mode class and injects PRINT_MODE_CSS; Row.tsx skips IntersectionObserver so ALL chart rows render; Tabs.tsx sets forceRender:true on every tab item and isComponentVisible=true on every tab's DashboardComponent
↓
6. Strip hidden-tab display:none — UNHIDE_TAB_PANELS_JS is evaluated. Because forceRender=true causes CSSMotion to render inactive panels with inline style="display:none", this JS removes that inline style from every [role="tabpanel"] element so they become visible to the layout engine
↓
7. Wait for all charts — PRINT_ALL_CHART_HOLDERS_READY_JS polls until every .dashboard-component-chart-holder (not just viewport-visible ones) reaches a terminal state
↓
8. Strip again, then PDF — UNHIDE_TAB_PANELS_JS is called a second time (safety, in case React reconciliation re-applied display:none during chart loading), then page.pdf() is called with A4 format, 10mm margins, print_background:true
↓
9. Return bytes or fall back — if any exception occurs, get_print_pdf() returns None, and _get_pdf() falls back to the existing screenshot path. No report failure.

URL Structure

/dashboard/1/&standalone=3&print=1
  • standalone=3 = DashboardStandaloneMode.REPORT — hides nav bar, header, and filter bar chrome
  • print=1 = new param (type: number) — triggers print-mode CSS and all virtualization bypasses. Separate from standalone. Standalone=3 alone does NOT trigger print mode.

4. Roadblocks Encountered & How Each Was Overcome

Roadblock 1: DEV_MODE=true skips npm run build in Docker

Problem: The docker-compose.yml has DEV_MODE: "true". When this is set, the Docker build process entirely skips the npm run build step. The frontend bundle served from /app/superset/static/assets/ is whatever was built before the container started — not the current source. Frontend changes made locally were silently ignored.

Discovery: Confirmed by reading the Dockerfile and seeing the conditional if [ "$DEV_MODE" = "true" ]; then ... skip build. Also confirmed that the assets directory is volume-mounted (./superset:/app/superset), so files written on the Mac host are immediately available in the container without a rebuild.

Fix: Frontend changes require running npm run build locally in superset-frontend/ on the Mac host. The build output lands in superset/static/assets/ which is volume-mounted into the containers. Critically, lightningcss.darwin-arm64.node was missing after the Docker build, so npm install in superset-frontend/ had to be run first on the Mac.

Roadblock 2: IntersectionObserver virtualization hides off-screen charts

Problem: The DashboardVirtualization feature flag, when enabled, uses IntersectionObserver in Row.tsx to set isInView=false for rows not near the viewport. When Playwright renders the full-height dashboard for PDF, the viewport is only the configured window height (~1200px). All rows below the fold have isInView=false, meaning their chart holders are empty containers — no charts mount and PRINT_ALL_CHART_HOLDERS_READY_JS would either wait forever or succeed vacuously.

Fix: In Row.tsx, read isPrintMode and initialize isInView to true when in print mode. Also guard the entire IntersectionObserver setup block with !isPrintMode && so the observer is never created in print mode.

Roadblock 3: CSS display:block !important cannot override React inline styles

Problem: With forceRender:true on tab items, @rc-component/motion CSSMotion.js (line 115) renders inactive tab panels but passes style={{ display: 'none' }} as a React prop to the rendered div. The actual DOM node gets an inline style attribute. CSS rules — even with !important — have lower precedence than inline style attributes. So the CSS approach (.ant-tabs-content { display: block !important }) was added, tested, and found to be completely ineffective.

Discovery: Traced through the exact call chain: TabPanelList/index.js → CSSMotion with forceRender=forceRender → CSSMotion.js line 115: else if (forceRender || !removeOnLeave && !leavedClassName) { motionChildren = children({ style: { display: 'none' } }) }. Confirmed with debug script that antTabsContentCount: 1 even with forceRender compiled into the bundle — the second panel was in the DOM but display:none.

Fix: UNHIDE_TAB_PANELS_JS — evaluated by Playwright from Python, outside React's reconciliation loop. It directly removes el.style.display on every tabpanel element. Because no React state changes, React does not re-render and does not re-apply display:none. Called twice: once before the readiness wait (so inactive charts can mount) and once immediately before page.pdf() (safety, in case any intervening render cycle re-applied it).

Roadblock 4: Only Tab 1 charts counted — PRINT_ALL_CHART_HOLDERS_READY_JS false positives

Problem: The original REPORT_CHART_HOLDERS_READY_JS filters chart holders by viewport visibility using getBoundingClientRect(). In print mode, tab 2's chart holders were not in the viewport (they were either display:none'd or off-screen). The readiness check returned true after only tab 1's 6 charts loaded, because it never saw tab 2's 4 chart holders. This produced a 23 KB PDF containing only tab 1.

Fix: Added PRINT_ALL_CHART_HOLDERS_READY_JS — an identical readiness check that omits the getBoundingClientRect() viewport filter. It checks ALL chart holders in the DOM. Combined with the UNHIDE fix (step 6 in the flow), tab 2's holders become visible and mount before this check runs.

Roadblock 5: ALERT_REPORTS_NOTIFICATION_DRY_RUN=True in main dev config

Problem: The main development config (superset_config.py) has ALERT_REPORTS_NOTIFICATION_DRY_RUN = True. This means reports execute the screenshot/PDF pipeline but do NOT actually send the notification (email/Slack). So even when the browser-print path produced correct output, the worker would log "dry run" and the report appeared to "succeed" with no actual PDF delivery to verify.

Fix: Added ALERT_REPORTS_NOTIFICATION_DRY_RUN = False to docker/pythonpath_dev/superset_config_docker.py, which is imported last and overrides the main config. This is dev-environment-only and must NOT go into the PR.

Roadblock 6: useLegacyItems strips forceRender? (false alarm)

Problem: Suspected that antd/es/tabs/hooks/useLegacyItems.js might strip forceRender from the items array, explaining why tab 2 didn't appear even after the forceRender fix was compiled.

Discovery: Read useLegacyItems.js source. It does return items.map(item => ({ ...item, destroyOnHidden: ... })) — the spread ...item preserves all fields including forceRender. This was not the cause.

Resolution: The real cause was Roadblock 3 (CSSMotion inline style). The forceRender was working correctly to render the second panel into the DOM — it just had display:none applied as an inline style afterward.

5. All Compromises Made — and How to Move to Final Implementation

This section is critical. The current implementation is a working Phase A/B/C prototype that proves the concept end-to-end. It contains deliberate compromises that must be addressed before this can be merged to main and enabled in production.

Compromise 1: Multi-URL dashboards silently fall back

What it is: Dashboards that have top-level tabs (where each tab is a separate "page" with its own permalink URL) produce multiple URLs. _get_browser_print_pdf() checks if len(urls) != 1: return None and logs a warning. The report falls back to the existing screenshot-stitch path.

Why it's a compromise: Multi-tab dashboards are common. A complete implementation would render each URL separately, get a PDF for each, and merge them using a library like pypdf.

Path to final: Phase 5 (multi-tab merge). For each URL in get_dashboard_urls(), call get_print_pdf() to get a bytes blob. Use pypdf.PdfWriter to append all pages. Return the merged PDF. The _get_browser_print_pdf() function already has the scaffolding — it's a matter of iterating and merging.

Compromise 2: No safety limits on page PDF generation time

What it is: get_print_pdf() uses SCREENSHOT_PLAYWRIGHT_DEFAULT_TIMEOUT as the Playwright context-level timeout and derives effective_wait from the budget/config for the readiness check. But page.pdf() itself has no explicit timeout — it uses the context default. For a very large dashboard (hundreds of charts), the PDF generation step itself could be slow.

Path to final: Pass an explicit timeout to page.pdf() derived from the remaining budget after the readiness wait. Also add a configurable BROWSER_PRINT_PDF_PAGE_TIMEOUT config key.

Compromise 3: JS unhide runs outside React lifecycle

What it is: UNHIDE_TAB_PANELS_JS directly mutates the DOM from Playwright's JS context. This bypasses React's reconciliation. In theory, if something triggers a React re-render between the final unhide call and page.pdf(), React could re-apply style="display:none". In practice this doesn't happen because the dashboard is in a stable state (all charts loaded, no pending state transitions), but it is technically fragile.

Path to final: The correct fix is to modify CSSMotion.js behavior upstream, or use a React context/flag that tells CSSMotion not to apply display:none when in print mode. A practical Superset-level approach: add a CSS variable or a data attribute (data-print="1") on the body, then add a CSS rule in printMode.ts that targets the specific antd/rc-tabs panel structure. However, since inline styles always win over CSS rules, the real solution is to override CSSMotion behavior. One approach: monkey-patch TabPanelList in print mode to pass visible={true} to every CSSMotion instance instead of the actual active state — this way CSSMotion never goes into the "forceRender" path at all, and the panel gets rendered with no display:none. This can be done by wrapping LineEditableTabs in a context that overrides the tab active key when in print mode.

Compromise 4: No chart-type allow-list or page-count budget

What it is: Some chart types (DeckGL, WebGL-based, large canvases) may not render correctly via Playwright's headless Chromium, or may produce very large PDFs. There is no allow-list of chart types that are safe for PDF, and no cap on the number of PDF pages generated.

Path to final: Phase 4 hardening. Add BROWSER_PRINT_PDF_CHART_TYPE_BLOCKLIST config (list of viz_type strings that trigger fallback). Add BROWSER_PRINT_PDF_MAX_PAGES config. After generating the PDF, check page count and fall back if it exceeds the limit.

Compromise 5: docker/pythonpath_dev/superset_config_docker.py enables the flag

What it is: For development/testing, the feature flag is turned on in the docker config override file. This file would normally be in .gitignore (it's a local override), but in this repo it exists and was modified.

Path to final: Remove the DASHBOARD_REPORTS_BROWSER_PRINT_PDF entry from the docker config before submitting the PR. The flag defaults to False in config.py and operators who want to enable it can set it in their own config override.

Compromise 6: No unit tests or integration tests

What it is: None of the new Python functions (DashboardPrintScreenshot, get_print_pdf(), _get_pdf() flag routing, _get_browser_print_pdf(), UNHIDE_TAB_PANELS_JS) have automated tests. The frontend changes (Row.tsx, Tabs.tsx, SliceHeader/index.tsx) also have no new test coverage.

Path to final (Python): Add unit tests in tests/unit_tests/utils/ for DashboardPrintScreenshot.__init__ (verify URL construction), _get_pdf() flag routing (mock feature_flag_manager and assert which branch runs), and _get_browser_print_pdf() (mock DashboardPrintScreenshot). Mock WebDriverPlaywright to avoid needing a real browser.

Path to final (frontend): Add Jest tests for Row.tsx print mode bypass (mock getUrlParam to return 1, assert IntersectionObserver is not created), Tabs.tsx forceRender (assert tabItems have forceRender:true when isPrintMode), SliceHeader (assert canExplore=false in print mode).

Compromise 7: No UPDATING.md entry or docs update

What it is: The UPDATING.md file should document the new feature flag. The docs/ directory should have a user-facing description of how to enable browser-print PDF reports.

Path to final: Add to UPDATING.md: "New feature flag DASHBOARD_REPORTS_BROWSER_PRINT_PDF enables native browser-print PDF generation for dashboard reports. When enabled, requires PLAYWRIGHT_REPORTS_AND_THUMBNAILS to also be True." Add docs entry under the reports section.

Compromise 8: Double UNHIDE_TAB_PANELS_JS call is a workaround

What it is: Calling UNHIDE_TAB_PANELS_JS both before the readiness wait and after is a belt-and-suspenders workaround for React potentially re-applying display:none. Ideally the DOM would be correct from the start without needing post-render mutation.

Path to final: The definitive fix is at the React level (see Compromise 3). Once the React-level fix is in place, UNHIDE_TAB_PANELS_JS becomes unnecessary and can be removed from webdriver.py. Leave it in place until the React fix is confirmed working in production.
